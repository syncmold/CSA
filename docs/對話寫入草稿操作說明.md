# 對話寫入操作說明

> 檔名沿用「草稿」，但範本與簽核流程已經沒有草稿與版本（Q137，2026-11-18）。本文件寫的是 **Q137 (7) ① 的暫行做法**：使用者同意先用，尚未定案，日後可能改成別的寫法。

稽核部提供的新問卷、新簽核名單格式不固定，系統不做匯入畫面（ADR-0006）。流程是：開發者把檔案交給 Claude → Claude 分析後經**對話寫入**的受控途徑寫進資料庫 → 稽核主管在系統畫面檢查。對話寫入只能**新增**：資料庫還沒有的範本編號（寫成**停用**，稽核主管檢查後改為啟用才會出現在年度發起），以及**停用範本**還沒有流程的「範本 × 廠區」（範本已啟用就擋下，42501 `template_active`：流程沒有狀態，寫給啟用中的範本等於直接能發起，請到簽核流程新增）。已有的範本與流程一律擋下，請到範本管理／簽核流程直接修改，所以 Claude 解析錯了，最多多一份要刪掉的停用範本或流程。實作決定見需求決策紀錄 Q90、Q137 (7)。

## 一、把稽核部的檔案交給 Claude

1. **檔案放在 repo 外**：照公司資料的慣例放進 `稽核/富群自評/<廠區>/` 底下（例如 `稽核/富群自評/福清富群(word檔)/`）。原檔含簽名與人名，**不得放進 csa-system repo**；`.gitignore` 也擋了 `*.doc`、`*.docx`。
2. **在 Claude Code 的對話裡說清楚**：
   - 檔案路徑，以及它是什麼：問卷範本（哪一份、哪些廠區適用）或簽核流程（哪一份範本 × 哪個廠區）。
   - 是新的一份，還是改既有的：一個編號只有一份範本、一個「範本 × 廠區」只有一條流程，沒有版本。**已經有的不能經對話寫入改**，請稽核主管在範本管理／簽核流程畫面直接修改（改的內容用在下一次發起與補發，已發出的自評表不受影響）。
   - 原檔有沒有已知的問題（拆錯的列、漏字），或哪些地方要等稽核部確認。
3. Claude 會依格式選做法：
   - **Word 問卷、格式和現有的一樣**：在 `scripts/templates/convert.mjs` 的範本清單加一筆，跑 `npm run templates:convert`，產生 `supabase/drafts/templates/<廠區>/<廠區代碼-紙本編號>.json`（去識別、只有控制要點文字與結構），再跑 `npm run templates:verify` 逐題比對 Word。這個檔案進版控。
   - **其他格式**（PDF、掃描檔、Excel、格式不同的 Word）：Claude 讀檔後直接寫一份同樣格式的定義檔（見下方「定義檔格式」），寫入前列出章節數、題數與有疑問的地方給你確認。
   - **簽核流程**：稽核室關卡的簽核人是真實的 OMS 工號，定義檔**放在 `supabase/drafts/local/`**（已在 `.gitignore`，不進版控），用完可以刪。廠區端的關卡不寫人名，自評表發出後由廠區負責人分派（#101）。
4. Claude 執行寫入：

   ```bash
   npm run drafts:write -- supabase/drafts/templates/FQ/FQ-04.json
   npm run drafts:write -- supabase/drafts/templates          # 整個資料夾（含各廠區的子資料夾）
   npm run drafts:write -- supabase/drafts/local/route-FQ-04.json
   ```

   每個檔案印一行結果（範本：幾章幾題、新範本是停用；流程：幾關）；同一批先寫範本、再寫流程。失敗的檔案會列出原因，其他照寫；已有的範本或流程就是失敗之一，重跑同一批不會取代或多建任何東西。

### 對話寫入做了什麼、擋了什麼

- `drafts:write` 以資料庫角色 **`csa_drafter`** 連線（主機與資料庫同 `CSA_DB_URL`，密碼是 `.env` 的 `CSA_DRAFTER_PASSWORD`，必填；舊的 `.env` 沒有這一行就照 `.env.example` 補上，再跑一次 `npm run db:init` 建好角色）。這個角色沒有任何資料表的權限，寫入只能經由 `draft_template` 與 `draft_route` 兩支函式（它也能執行幾個依登入身分判斷的唯讀函式，對它一律回「否」）。日後新增的資料庫函式照慣例要 `revoke execute … from public`，否則這個角色也能執行。
- `draft_template`：資料庫還沒有這個編號就新增一份**停用**的範本（抬頭、適用廠區、章節、控制要點）；已有同編號的範本（不論啟用、停用）就拒絕，提示「已在使用，請到範本管理直接修改」（42501，`template_exists`）。定義帶了 `version` 或 `status`，或有空白的章節名稱、控制要點文字，也拒絕。自評單位以名稱對應集團共用清單，清單沒有的會新增。限定廠區（`allPlants: false`）卻沒給 `factoryCodes` 時照樣寫入，`drafts:write` 會印出 ⚠ 提醒，由稽核主管在抬頭補上。
- `draft_route`：範本還是停用、這個「範本 × 廠區」還沒有流程，就新增一條；已有流程就拒絕，提示「請到簽核流程直接修改」（42501，`route_exists`）；範本已啟用也拒絕，提示「流程請到簽核流程直接新增或修改」（42501，`template_active`）。流程沒有狀態，寫入後就是那個組合的流程；稽核主管檢查範本與流程後把範本改為啟用，流程通過發起檢查，年度發起時就能勾選。範本、廠區、可編輯範圍的自評單位都要已經存在，打錯就整份拒絕；定義帶了 `status` 或 `templateVersion` 也拒絕。
- 兩支函式都會把交易標成「走對話寫入」，並記下這個交易新建的範本或流程 id；資料庫觸發器（`guard_draft_path`）看到標記，只放行歸這些 id 管的資料，自評單位只能新增不能改名或刪除；函式本身寫錯也碰不到既有的範本與流程（`tests/db/draft_path.test.ts` 驗證）。日後定案改成別的寫法（例如覆寫停用中的範本），只改兩支函式決定寫到哪裡的部分，觸發器與 `csa_drafter` 不動。

## 二、稽核主管檢查並啟用

### 問卷範本（範本管理 `/admin/templates`）

1. 剛寫進來的範本是「停用」：清單預設隱藏停用的範本，打開上方「顯示停用的範本」才看得到（Q87 (6)）。進範本頁看抬頭（編號、名稱、**組成要素**：要素類範本沒有給 `component`、編號又不是 A–D 開頭時會是「未分類」，按「修改」再用「編輯抬頭」選好；**適用廠區**：空白就按「修改」再用「編輯抬頭」補上，否則年度發起和簽核流程都用不到這份範本）與「內容：N 章、M 個控制要點」，和 Claude 回報的題數、紙本對一下。
2. **抽查**：挑幾個章節，逐題對紙本或 Word 原檔的章節名稱、控制要點文字、自評單位與順序。特別看：
   - 紙本上同一格控制要點由幾個單位各答一列的，系統裡是一個控制要點掛幾個自評單位（03.1、04、05 有，Q92）。
   - 自評單位是「待指定單位」的（10.1、15）：稽核部確認後，到「自評單位清單」把它改名成正式名稱，一次全部生效。若兩份要掛不同單位，先改其中一份的控制要點。
   - 多層章節（10.1 的「作業→階段→小節」）照原檔分層：第 1 層一張卡片，階段與小節是卡片裡的分段列，上層只出現一次（Q125）。台北總公司 A～D 的題號在 # 欄、文字裡沒有題號。
3. 有錯就直接在範本頁修改；要整份重寫就「刪除範本」後請 Claude 改定義檔重跑（從未使用過的範本才能刪，Q87；重跑不會取代既有的範本）。**有簽核流程掛在這份範本上時，範本算「已使用」、刪除鈕會停用**：先到簽核流程把那幾條流程刪掉（要輸入「刪除 ＜範本編號＞」），再回來刪範本。
4. 沒問題就按右上角「修改」，再按「編輯抬頭」，狀態選「啟用」後儲存，最後按「完成修改」（點名稱進來的範本頁只能查看，#66）。啟用後才會出現在年度發起。

### 簽核流程（簽核流程 `/admin/flows`）

1. 寫進來的流程列在對應的「範本 × 廠區」下（每個組合只有一條，沒有狀態）。進編輯頁核對每一關的關卡名稱、群組（廠區端／稽核室覆核）、稽核室關卡的簽核人與可編輯範圍；簽核人工號已不在 OMS 名單的會標示出來。
2. 發起檢查（清單與編輯頁隨時顯示）沒過的，按右上角「修改」（點名稱進來的流程頁只能查看，#66），依提示補關卡或改可編輯範圍。沒通過的組合在年度發起時不能勾。
3. 整條不要就在編輯頁刪除：要親手輸入「刪除 ＜範本編號＞」（不能貼上），已發出的自評表不受影響。

## 三、定義檔格式

JSON，`kind` 決定交給哪一支函式；其他沒列的鍵（例如 `generatedBy`）會被忽略。

### 問卷範本（`kind: "template"`）

```json
{
  "kind": "template",
  "code": "FQ-04",
  "name": "存貨循環",
  "layout": "control_activity",
  "allPlants": false,
  "factoryCodes": ["FQ"],
  "sections": [
    {
      "name": "存貨分類編號作業",
      "controlPoints": [
        { "text": "各存貨是否符合一料一號，一號一料之原則？", "assessingUnits": ["工程單位"] }
      ]
    },
    {
      "name": "物料標示與追溯性管理作業",
      "controlPoints": [
        { "text": "製程階段之物料標示是否依既定之作業程序確實遵循？", "assessingUnits": ["品保單位", "生產單位", "資材單位"] }
      ]
    }
  ]
}
```

- `layout`：`control_activity`（控制作業的循環 01–15，每個控制要點的 `assessingUnits` 至少一個）或 `element`（其他組成要素 A–D，`assessingUnits` 可以是空陣列，也可以多個）。這兩個值是開發內部用語，畫面上不會出現（Q101(5)）。
- `component`（選填）：組成要素，`control_environment`、`risk_assessment`、`control_activities`、`information_communication`、`monitoring` 其中之一，要和 `layout` 對得上（`control_activities` 一定是 `control_activity`）。沒給時控制作業自動歸類，其他依編號開頭 A–D 推定，推不出來就是「未分類」（Q101(7)）。
- `assessingUnits`：自評單位名稱的清單，依作答順序（紙本上的列順序）。紙本同一格控制要點由幾個單位各答一列（Word 垂直合併）時，就是**一個控制要點帶多個單位**，不要拆成幾個控制要點（#46、Q92）。同一題不能重複同一個單位。舊格式的單一 `assessingUnit` 不再接受，會整份拒絕。
- `allPlants: true` 時 `factoryCodes` 留空；否則列 OMS 廠區代碼（大小寫、空白不拘）。
- 不寫 `version`（範本沒有版本）、也不寫 `status`（一律寫成停用），寫了整份拒絕。
- 章節與控制要點的順序就是陣列順序。
- 多層章節（Q125）：章節的 `level` 是 2 或 3（第 1 層不寫），第一個章節是第 1 層，往下一次只能深一層，否則整份拒絕。只當上層標題的章節 `controlPoints` 給空陣列，後面接著更深一層的章節。
- 原檔題號（Q125）：章節與控制要點可以帶 `code`（「1.1」「1.1.1-1」，照原檔寫法），`name`／`text` 就不再包含題號；沒有原檔題號的不寫，畫面在同一張卡片內依序編號。
- 控制要點的換行（Q126）：`text` 可以有換行（JSON 寫 `\n`），照原檔寫完一句才換的行（括號說明、條列項，條列項前面寫「· 」）；畫面與 PDF 照換行顯示。

  ```json
  { "name": "董事會與高階管理階層應重視誠信與道德價值。", "code": "1", "controlPoints": [] },
  { "level": 2, "code": "1.1", "name": "公司是否建立內部行為準則…？",
    "controlPoints": [{ "code": "1.1.1-1", "text": "公司是否建立董事行為準則？", "assessingUnits": [] }] }
  ```

### 簽核流程（`kind: "route"`，不進版控）

```json
{
  "kind": "route",
  "templateCode": "FQ-04",
  "factoryCode": "FQ",
  "steps": [
    { "name": "自行檢查人員－資材單位", "group": "plant", "editableUnit": "資材單位" },
    { "name": "課長", "group": "plant", "editableUnit": null, "branchUnit": "資材單位" },
    { "name": "部門主管－資材單位", "group": "plant", "editableUnit": null, "branchUnit": "資材單位" },
    { "name": "廠區經理人", "group": "plant", "editableUnit": null },
    { "name": "台北稽核人員", "group": "audit_review", "signer": "<OMS 工號>", "editableUnit": null, "link": "taipei_auditor" },
    { "name": "稽核主管", "group": "audit_review", "signer": "<OMS 工號>", "editableUnit": null, "link": "audit_chief" }
  ]
}
```

- 不寫 `templateVersion` 與 `status`（範本沒有版本、流程沒有狀態），寫了整份拒絕。
- `group`：`plant`（廠區端）或 `audit_review`（稽核室覆核，只能唯讀，`editableUnit` 必須是 `null`）。
- `signer`：只有 `audit_review` 要寫 OMS 工號；`plant` 不寫，寫了也不看（廠區端的人發起後由廠區負責人分派，#101）。
- `editableUnit`：這一關可以作答的自評單位名稱；`null` 是唯讀（主管、稽核關卡）。範本用到的每個自評單位都要有一個自行檢查人員關卡（它就是那條分流的第一關），而且至少要有一個匯流後的關卡，否則發起檢查不會過（#98）。
- `branchUnit`：這一關屬於哪個自評單位的分流（Q116）。部門主管、稽核部多加的那一關（例：課長）要填，填它所屬單位的名稱；自行檢查人員關卡不用填（跟著 `editableUnit`）；廠區經理人與稽核室覆核不填（匯流後）。名稱必須在自評單位清單上，打錯整份拒絕。沒填的部門主管會變成匯流後的關卡，等所有單位都完成才依序簽核。同一條分流的關卡依陣列順序，第一關必須是自行檢查人員，所以多加的那一關要排在它後面（上例的課長）。
- `link`（#189）：連動標記，只有 `audit_review` 能填，值 `taipei_auditor`（台北稽核人員）或 `audit_chief`（稽核主管），沒填就是一般關卡。每條流程這兩種各要有一個，名稱必須就是「台北稽核人員」「稽核主管」，稽核主管要排在最後一關，否則發起檢查不通過（名稱不對整份拒絕）；有標記的關卡寫好後在流程編輯器唯讀（不能改名、改簽核人、刪除），簽核人由權限管理決定（連動本身之後的工單才做，目前仍是上面 `signer` 寫的人）。同一種標記寫兩次整份拒絕。

## 四、之後延伸到內控文件（#39）

內控文件、條文與內控依據的資料表在 #9 建立後，#39 會加一支 `draft_control_procedure`（同樣先標記對話寫入、只給 `csa_drafter`），在 `guard_draft_path` 加上那幾張表的判斷並掛上觸發器，再在 `drafts:write` 的 `KINDS` 加一種 `kind`。交付與檢查步驟屆時補在本文件。
