# 前端技術選型說明

> 對象：本系統開發者（學習用，以及日後要更換某個套件時評估影響範圍）
> 範圍：Q47 定案的 6 個前端模塊。後端是 Supabase（Postgres＋RLS＋資料庫函式），不在本文範圍內。
> 版本：專案初始化時以當下的穩定版為準，並在 `package.json` 鎖定確切版本；React 主版本要選 Ant Design 官方支援的版本。

## 1. 全貌：六個模塊各管什麼

```
┌───────────────────────── 瀏覽器 ─────────────────────────┐
│ ⑤ React Router       網址 → 要顯示哪個頁面、權限守門        │
│   └ ① React + TS     頁面元件（畫面 = 資料的函式）          │
│       ├ ② Ant Design  表格、表單、對話框等現成元件           │
│       ├ ③ i18next     t('key') → 目前語言的文字             │
│       └ ④ TanStack Query  快取、載入中、錯誤、重新抓取      │
│             └ ④ supabase-js  實際發出 HTTP 請求             │
└──────────────────────────┬───────────────────────────────┘
                           │ HTTPS（PostgREST 查詢 / RPC 呼叫函式）
                ┌──────────┴──────────┐
                │ Supabase：Postgres   │  ← 誰能看、誰能改、簽核往哪走
                │ ＋RLS＋資料庫函式    │     都在這裡判斷（Q33）
                └─────────────────────┘

開發時：① 裡的 Vite 把 .ts / .tsx 即時編譯；上線前打包成靜態檔放上網站
驗證時：⑥ Vitest 測單一函式和元件；⑥ Playwright 開真的瀏覽器跑完整簽核
```

| # | 模塊 | 採用 | 一句話職責 |
|---|---|---|---|
| ① | 框架與語言、建置 | React＋TypeScript＋Vite | 把畫面拆成元件；用型別防錯；開發和打包 |
| ② | UI 元件庫 | Ant Design | 提供表格、表單、驗證、對話框，內建五種語系 |
| ③ | 多語系 | react-i18next | 介面文字依使用者選的語言切換 |
| ④ | 讀寫資料 | supabase-js＋TanStack Query | 跟資料庫溝通，並管理快取和載入狀態 |
| ⑤ | 頁面路由 | React Router | 網址對應頁面、頁面參數、登入守門 |
| ⑥ | 測試 | Vitest＋Playwright | 單元測試＋端對端測試 |

## 2. 一個動作走完六個模塊：部門主管按「核准」

```
 1 主管點通知信連結 /assessments/123
      ⑤ Router：比對路由 → 顯示 AssessmentPage，帶入參數 id=123
      ⑤ 守門：目前沒有身分 → 導回切換身分頁（demo）或登入頁（正式版）

 2 AssessmentPage 載入資料
      ④ useQuery(['assessment',123]) → supabase-js 查 assessment
      後端 RLS：只回傳「這個人有權看」的資料
      ④ 抓資料期間 isLoading=true → ② 顯示 <Spin> 轉圈

 3 畫面呈現
      ② <Table> 依控制要點逐列顯示；依「本關可編輯範圍」決定哪些欄位唯讀（Q13）
      ③ 欄位標題、按鈕文字都是 t('form.approve') 之類的呼叫 → 依語言顯示
      ② <ConfigProvider locale> 讓日期、分頁、空表格提示也跟著換語言

 4 按「核准」
      ② <Modal> 讓主管填意見
      ④ useMutation → supabase.rpc('approve_step', {assessment_id:123, comment})
      後端函式：確認目前關卡是本人 → 寫簽核記錄（帳號、時間）→ 推進到下一關

 5 更新畫面
      ④ 成功後 invalidateQueries(['assessment',123], ['my-tasks'])
         → 相關資料自動重抓，畫面不用手動刷新
      ② message.success(t('form.approved'))
      ⑤ navigate('/my-tasks') 回到待簽清單

 6 測試怎麼保護這條路
      ⑥ Vitest：測 canEdit(控制要點, 關卡) 這類純函式，以及按鈕在唯讀時是否停用
      ⑥ Playwright：開真的瀏覽器，用切換身分從第 1 關一路簽到第 6 關，
         並檢查匯出的 PDF 上有 6 筆簽核記錄
```

## 3. 各模塊說明

### ① React＋TypeScript＋Vite

**是什麼**
- React：把畫面寫成「元件」。元件是一個函式，輸入資料、輸出畫面；資料一變，畫面自動更新。
- TypeScript：替 JavaScript 加上型別，在編譯階段就抓出「把字串當數字用」「欄位名稱打錯」這類錯誤。
- Vite：開發伺服器（存檔後畫面立刻更新）兼打包工具（產出可以直接上架的靜態檔）。

**選它的原因**

| 比較對象 | 為什麼不選 |
|---|---|
| Vue、Angular | Vue 一樣好用，但 aios 專案已經用 React，小組有經驗；Angular 對這個規模太重 |
| 原生 JS 單一 HTML | 五種語系、流程編輯器、四種角色的畫面，單一檔案會超過一萬行，無法維護 |
| Next.js | 它的強項是伺服器端渲染；本系統是內部工具，不需要 SEO，靜態網站就夠，也能免費放上 GitHub Pages |

TypeScript 還有一個關鍵好處：可以從資料庫結構**自動產生型別**（`supabase gen types`）。資料表欄位改名時，前端所有用到的地方會直接編譯失敗，不會等到上線才出錯。

**在本系統的運作**
- 每個畫面都是元件：`AssessmentPage`、`ControlPointRow`、`SignTable`、`FlowEditor`…
- **業務規則只在資料庫寫一份**（ADR-0001）：誰能改哪些控制要點、送出前缺什麼，都由資料庫函式判斷並回傳結果，前端照結果顯示。`src/domain/` 只放**呈現用的純函式**，例如把資料庫回傳的錯誤清單對應到畫面上的控制要點、計算簽核歷程的顯示順序；這些函式不依賴 React，可以單獨測試。例外有兩個。一是答題頁的「已答 a／b 題」（#134）：它要算畫面上還沒暫存的答案，所以一題算不算答完由 `isAnswered` 在瀏覽器再寫一份，和資料庫的 `answer_is_complete` 同一條規則，`tests/db/answer_progress.test.ts` 逐一比對兩邊；送出時缺什麼仍只由資料庫判斷。二是匯入分派表的寫入規則（#180、Q130 (4)）：不在 OMS、已離職的人那幾格不寫入、超過一半廠區不同要勾選，由 `src/domain/assignmentSheet.ts` 的 `importPlan` 判斷，因為它依據的 OMS 比對只有 CSA 後端（`exchange/omsMatch.ts`）問得到，資料庫問不到；誰能改哪一關、已簽不能換仍只由資料庫（`assign_step_signer`）判斷。

**更換的影響（最大）**
- 換掉 React 等於前端重寫：②、③、④ 的 TanStack Query 部分、⑤ 都是 React 專用的套件，要一起換掉。
- 不受影響的部分：`src/domain/` 的純函式、`src/api/` 的資料存取、翻譯檔、資料庫、Playwright 測試。
- 換掉 Vite：要改建置設定和環境變數寫法（`import.meta.env`）；Vitest 共用 Vite 的設定，也要跟著換。

### ② Ant Design

**是什麼**：企業後台用的 React 元件庫，提供表格、表單、日期選擇、對話框、選單、通知等元件。

**選它的原因**

| 比較對象 | 差異 |
|---|---|
| MUI（Material UI） | 也很完整，但偏消費型產品的風格；複雜表格的進階功能要付費 |
| Mantine、shadcn/ui | 比較輕量、好客製，但大型表格和表單驗證要自己組裝 |
| **Ant Design** | 表格（固定欄、合併儲存格、可編輯列）和表單驗證都是強項；**繁中、簡中、越南文、泰文、英文的語系包全部內建** |

**在本系統的運作**
- 問卷答題：`<Table>` 照紙本矩陣，選項放在表頭，一個控制要點的每個自評單位各一列，控制要點以 rowSpan 合併成一格（#46、Q92）；勾選格是瀏覽器原生的同名 `<input type="radio">`（Tab 進區塊、方向鍵切換，aria-label 寫明題號、單位、欄位與選項）；唯讀時加 `disabled`（Q13）。
- 必填驗證（Q18）：`<Form>` 的 `rules`，例如「勾了否，改善措施就必填」，而且即時在欄位下方提示。整份表單送出時，後端函式會再檢查一次，前端提示只是為了使用體驗。
- 流程編輯器（Q16）：用 `<Table>` 加拖曳排序，或用 `<Steps>` 顯示關卡。
- 追蹤總覽（Q21）：`<Table>` 的篩選和排序；Excel 匯出另外用 `write-excel-file`（#14、Q95；畫面與 Excel 的文字出自同一組純函式）。
- 切換語言：`<ConfigProvider locale={…}>` 跟 ③ 連動。

**更換的影響（大）**
- 所有頁面的畫面程式要改寫，表單驗證寫法也要重做。
- 語系包要另外處理：Ant Design 內建五語，換掉後可能要自己補越南文或泰文。
- Playwright 測試如果用 Ant Design 的 CSS class 定位元素會壞掉。**規範：測試一律用角色、文字或 `data-testid` 定位。**
- 不受影響的部分：業務規則、資料存取、路由、翻譯檔。

### ③ react-i18next

**是什麼**：程式裡不寫死文字，改寫成 `t('form.approve')`；套件依目前語言，到對應的翻譯檔取出文字。

```
src/locales/zh-TW/common.json   { "form": { "approve": "核准" } }
src/locales/vi/common.json      { "form": { "approve": "Phê duyệt" } }
```

**選它的原因**

| 比較對象 | 差異 |
|---|---|
| react-intl（FormatJS） | 功能相當，但寫法較繁瑣 |
| 自己寫一個字典物件 | 複數規則、變數插值、語言切換、找不到翻譯時的備援都要自己做 |
| **react-i18next** | React 生態最普及；支援分檔載入、找不到翻譯時退回繁中、自動偵測語言 |

**在本系統的運作**
- 介面文字：所有按鈕、標題、錯誤訊息都走 `t()`。
- 語言決定順序：使用者手動選的 → 依 OMS 廠區代碼推算（Q19）→ 繁中。手動選擇存在瀏覽器裡。
- 切換語言時同步三件事：i18next 語言、Ant Design 的 `ConfigProvider locale`、日期函式庫 dayjs 的語系。
- **控制要點內容不走 i18next**：控制要點存在資料庫，譯文是資料表欄位（Q20）。i18next 只管程式裡的固定文字。這是兩套不同的機制，不要混用。

**更換的影響（中）**
- 要把所有 `t()` 呼叫換成新套件的寫法，可以用全域取代或腳本批次處理。
- 翻譯檔是通用的 key-value JSON，大多可以直接沿用。
- 要重新接上 Ant Design 和 dayjs 的語系連動。

### ④ supabase-js＋TanStack Query

**是什麼**
- supabase-js：Supabase 官方的 JS 函式庫。查資料表會轉成 PostgREST 的 HTTP 請求，呼叫資料庫函式用 `rpc()`；請求會自動帶上身分 token，讓後端 RLS 判斷。
- TanStack Query：管理「伺服器上的資料」：快取、載入中與錯誤狀態、資料過期時重抓、寫入後讓相關資料失效。

**為什麼要兩個**：supabase-js 只負責「把請求送出去」。如果只用它，每個頁面都要自己處理載入中、錯誤、快取、重抓，很容易出現畫面上是舊資料的 bug。TanStack Query 把這些統一處理掉。

**選它的原因**

| 比較對象 | 差異 |
|---|---|
| SWR | 較輕量，但寫入後讓相關資料失效（mutation 加 invalidation）的支援較弱 |
| Redux＋RTK Query | 功能完整，但概念和樣板程式碼較多 |
| **TanStack Query** | 讀取（query）和寫入（mutation）都是一等公民；開發工具可以直接看到快取內容 |

**在本系統的運作：三層分工**

```
src/api/assessments.ts  ← 唯一直接呼叫 supabase-js 的地方
  export async function approveStep(assessmentId, comment) {
    const { error } = await supabase.rpc('approve_step', { assessment_id: assessmentId, comment })
    if (error) throw error
  }

src/hooks/useAssessments.ts  ← 用 TanStack Query 包裝
  export const useApproveStep = () => useMutation({
    mutationFn: ({ assessmentId, comment }) => approveStep(assessmentId, comment),
    onSuccess: (_, { assessmentId }) => {
      queryClient.invalidateQueries({ queryKey: ['assessment', assessmentId] })
      queryClient.invalidateQueries({ queryKey: ['my-tasks'] })
    },
  })

src/pages/AssessmentPage.tsx  ← 頁面只呼叫 hook，不知道背後是 Supabase
```

**更換的影響（設計成小）**
- **這一層就是 Q9「資料庫可搬遷」的接縫。** 日後離開 Supabase、改成自己的 API 伺服器時，只要改寫 `src/api/`；只要函式簽名不變，hooks 和頁面都不用動。前提是遵守規範：**頁面和 hooks 不准直接 import supabase-js。**
- 換掉 TanStack Query（例如換成 SWR）：只改 `src/hooks/`。
- 登入方式（OPEN-2）也在這一層：demo 用切換身分，正式版接 OMS 換證。換掉的只是「怎麼取得 session」，上層不受影響。

### ⑤ React Router

**是什麼**：決定網址對應哪個頁面，並提供頁面參數（`/assessments/:id`）、換頁（`navigate`）和巢狀版面。

**選它的原因**

| 比較對象 | 差異 |
|---|---|
| TanStack Router | 網址參數型別更嚴謹，但較新、資料較少 |
| 自己用 if 判斷網址 | 上一頁、重新整理、深層連結（通知信直接連到某張單）都要自己處理 |
| **React Router** | React 生態的事實標準，文件和範例最多 |

**在本系統的運作**

```
/                     → 依角色導向：簽核人到「我的待簽」，稽核到「追蹤總覽」
/my-tasks             → 我的待簽清單
/assessments/:id      → 單張自評表（答題或簽核）
/assessments/:id/pdf  → 預覽或匯出 PDF
/admin/templates      → 範本管理（稽核管理者）
/admin/flows          → 流程編輯器（稽核管理者）
/admin/launch         → 年度發起（稽核管理者，#12）
/admin/tracking       → 追蹤總覽
```

- 守門元件：沒有身分就導到切換身分或登入頁；角色不符就顯示「無權限」。
- **注意**：前端守門只是使用體驗。真正的權限擋在後端 RLS，就算有人直接打 API 也拿不到資料。
- GitHub Pages 是靜態主機，直接重新整理 `/assessments/123` 會找不到頁面。上線時要用 `404.html` 轉址，或改用 HashRouter（網址變成 `/#/assessments/123`）。

**更換的影響（中小）**
- 路由表集中在一個檔案，換套件時主要改這裡。
- 頁面裡的 `useParams`、`useNavigate`、`<Link>` 要換成新寫法，可以批次取代。
- 守門元件要重寫，但它只是呼叫 ④ 的「取得目前身分」。

### ⑥ Vitest＋Playwright

**是什麼**
- Vitest：單元測試和元件測試。毫秒級執行，存檔就自動重跑。
- Playwright：端對端測試。開真的 Chromium、Firefox 或 WebKit，模擬使用者點擊和輸入。

**為什麼要兩種**

| | Vitest | Playwright |
|---|---|---|
| 測什麼 | `canEdit()`、`validateBeforeSubmit()`、單一元件的行為 | 從打開網址、答題、六關簽核到匯出 PDF 的完整流程 |
| 速度 | 非常快，數百個測試幾秒跑完 | 慢，一條流程要數十秒 |
| 抓得到的問題 | 規則寫錯 | 各部分沒接好，例如 RLS 擋錯人、按鈕沒反應 |

**選它的原因**
- Vitest 跟 Vite 共用設定，不用另外設定編譯；寫法跟業界常見的 Jest 幾乎一樣。
- Playwright 的元素等待機制比 Cypress 穩定，可以多瀏覽器平行執行，失敗時自動錄影和截圖，而且免費。

**在本系統的運作**
- Vitest 必測：對本機 Supabase 呼叫資料庫函式，驗證每一關的可編輯範圍（Q13）、必填驗證（Q18）、退回後從哪一關重簽（Q17）；純前端只測語言決定順序（Q19）與呈現用函式。
- Playwright 必測：
  1. 6 個身分依序簽核到結案；
  2. 中途退回再重簽；
  3. 中途匯出 PDF，簽核欄只顯示已簽的關卡；
  4. 切換越南文後，介面文字確實改變。
- 對話寫入（Q28）的流程和範本（寫入後是停用），啟用前也可以用 Playwright 跑一次冒煙測試。

**更換的影響**
- Playwright 是黑箱測試，只看瀏覽器畫面，**前端框架全換也能沿用**。前提是用角色、文字或 `data-testid` 定位元素，不依賴 Ant Design 的 class。
- Vitest 跟 Vite 綁在一起：換掉 Vite，Vitest 也要換（例如換成 Jest），但測試內容幾乎可以照搬。

## 5. 建議目錄結構

```
src/
  api/        ④ 資料存取，唯一接觸 supabase-js 的地方
  hooks/      ④ TanStack Query 包裝
  domain/     呈現用純函式（錯誤清單對應、歷程排序…），Vitest 測試對象
  pages/      ① 頁面元件，由 ⑤ 路由對應
  components/ ① 共用元件（ControlPointRow、SignTable…），由 ② 組成
  locales/    ③ 翻譯檔 zh-TW / zh-CN / vi / th / en
  pdf/        PDF 產生模組（Q45，日後可加伺服器簽章）
  auth/       身分提供者介面：demo 切換身分／正式版 OMS（Q42、OPEN-2）
  router.tsx  ⑤ 路由表與守門
supabase/
  migrations/ 資料表、RLS、資料庫函式（Q48）
e2e/          ⑥ Playwright 測試
```
