# 部署與切換手冊

這份說明 CSA 有哪些環境、設定放哪裡、怎麼部署，以及怎麼從測試資料庫切換到正式資料庫。

## 1. 環境

| 環境 | 部署指令的名稱 | GitHub Environment | 用途 |
|---|---|---|---|
| 測試 | `test` | `test` | 試用、驗收。資料可以清掉重來（`reset`、`rebuild` 只在這裡能用） |
| 正式 | `prod` | `production` | 正式資料。不能 `reset`、不能 `rebuild`；`restore` 要加 `--confirm-prod` |

兩個環境各有自己的 Supabase 專案和前端託管專案，**金鑰一律各自產生**（特別是 `CSA_JWT_SECRET`），這樣測試環境簽出的 token 在正式環境無效。

程式碼只有一份。環境之間的差別只有「設定」，沒有程式碼分支。

## 2. 設定放哪裡

部署指令依序找設定：

1. 本機檔案 `<csa-deploy>/.env.deploy.<環境>`（預設在專案資料夾旁邊的 `csa-deploy/`，可用 `CSA_DEPLOY_DIR` 指定）。
2. 找不到檔案時，讀環境變數。GitHub Actions 就是這樣把 Environment 的 secrets 傳進來。

**正式環境請用第 2 種**：設定放在 GitHub 的 Environments，不放在任何人的電腦，這樣誰有權限誰就能部署，換人也不會斷。

| 名稱 | 種類 | 說明 |
|---|---|---|
| `SUPABASE_DB_URL` | secret | Supabase 的 Session pooler 連線字串（帳號是 `postgres.<專案代碼>`） |
| `SUPABASE_ANON_KEY` | secret | 該專案的 anon key（會寫進前端，本來就是公開值，但仍照環境分開存） |
| `CSA_JWT_SECRET` | secret | 該專案的 Legacy JWT Secret，換證用它簽 session token |
| `OMS_CHANNEL_KEY` | secret | OMS 的 CSA 專用查詢通道金鑰，由 OMS 維護單位交付 |
| `SUPABASE_ACCESS_TOKEN` | secret | 部署 Edge Function 用（Actions 用；本機改用 `npx supabase login`） |
| `VERCEL_TOKEN` | secret | 部署前端用（目前的前端託管是 Vercel；見第 7 節） |
| `CSA_SITE_URL` | variable | 使用者開啟的網址。換證只回應這個來源，**prod 必填** |
| `CSA_VERCEL_PROJECT` | variable | 前端託管專案名稱，**必填**（沒有預設值，填錯會在 Vercel 上建出新專案） |
| `CSA_REQUIRE_OMS_AUTH` | variable | OMS 授權頁勾了 CSA 才放行；OMS 端還沒設定好之前維持 `false` |
| `VITE_OMS_URL`、`VITE_OMS_ANON_KEY` | variable | OMS 專案的網址與 publishable key |
| `PROD_DEPLOYERS` | variable | 只在 `production`：允許部署正式環境的 GitHub 帳號，逗號分隔 |
| `CSA_SEED_AUDIT_CHIEF` | variable | 第一次初始化：第一位稽核主管的工號 |
| `CSA_SEED_MAINTAINERS` | variable | 第一次初始化：系統維護員工號，逗號分隔 |
| `CSA_SEED_ALLOWLIST` | variable | 第一次初始化：其他要放行的工號，逗號分隔 |

## 3. 日常部署

PR 合併進 `main` 之後：

- **用 GitHub Actions（建議）**：Actions → Deploy → Run workflow，選環境，步驟選 `update`。部署 `prod` 時，workflow 會先檢查觸發的人是否在 `production` Environment 的變數 `PROD_DEPLOYERS` 名單上（GitHub 帳號，逗號分隔），不在就拒絕。
- **用本機**：在乾淨的 `main` 上執行 `npm run deploy -- test update`。

`update` 依序做：`db`（套 migration）→ `drafts`（新範本，寫成停用）→ `function`（換證服務）→ `web`（前端）。先資料庫後前端。

安全閘門（不用靠人記得）：

- 只有 `main`、沒有未 commit 的修改、且和 `origin/main` 一致時才會部署。
- `function` 步驟部署後會檢查換證回應：「放行全開」和「開發期直接登入」必須都是關閉，否則部署失敗。
- `web` 步驟 build 後會掃描產物，裡面若有任何金鑰或非 anon 的 JWT 就拒絕發布。

## 4. 第一次建一個環境

1. 建 Supabase 專案（**正式環境不要用免費方案**：免費專案閒置會被暫停）。
2. 建 GitHub Environment（`test`、`production`），填第 2 節的設定。`production` 設 `PROD_DEPLOYERS`。
3. 跑 `all`：`check`（連線）→ `db`（結構）→ `seed`（放行名單、第一位稽核主管、範本）→ `docs` → `function` → `web`。
4. 用稽核主管的帳號登入驗證。其他人在「權限管理」頁加入。

`seed` 只在放行名單是空的時候才設角色與範本；已初始化過的環境重跑只補放行名單，不會蓋掉現場的修改。

## 5. 從測試資料庫切到正式資料庫

目標：不中斷維運、不弄丟測試期間確認過的內容、最後才刪測試資料庫。

1. **建好正式環境**，照第 4 節做到可以登入。這時測試環境完全不受影響。
2. **決定測試環境上有什麼要帶過去。** 稽核部在測試環境確認過的範本和簽核流程，如果正式版要沿用：
   - 先對測試環境跑 `backup`。
   - 把需要的資料匯入正式資料庫。**不要整個 `restore` 到正式環境**，那會把測試的人員資料、年度作業和測試單據一起帶過去；只帶範本、簽核流程這類設定資料，並事先決定要帶哪幾張表。
   - 正式版的放行名單與角色，用 `seed` 與「權限管理」頁重建，不從測試複製。
3. **確認設定沒有串到測試。** 正式 Environment 的 `SUPABASE_*`、`CSA_JWT_SECRET`、`CSA_SITE_URL` 都是正式專案的值。前端的 `VITE_*` 是 build 時寫進去的，所以切換後一定要重新跑 `web`（`update` 會做）。
4. **驗證。** 跑 `check`；用真實帳號走一遍登入、填一份、簽核、匯出 PDF；確認登入卡片上沒有「測試環境」標籤。
5. **備份。** 確認正式環境的備份排程已經在跑（第 6 節），再繼續。
6. **公告切換時間，使用者改用正式網址。**
7. **最後才刪測試資料庫。** 先對測試環境再做一次 `backup`，備份存到公司的共用位置，保留一段時間（例如 3 個月）再刪。

切換期間 `prod` 永遠不跑 `reset`、`rebuild`。

## 6. 備份與維運（正式環境）

- `backup` 把 `public` 與 `csa_meta` 兩個 schema `pg_dump` 到 `<csa-deploy>/backups/`。**正式環境不能只放個人電腦**：請排程（例如 GitHub Actions 的 schedule）執行 `pg_dump`，把檔案存到組織的儲存空間或公司共用磁碟，並定期做還原演練。
- Supabase 付費方案另有自己的每日備份，兩者並行。
- 至少兩位部門成員有部署權限（GitHub Environment 的 reviewers 與 repo 的 write 權限），避免只有一個人能維運。
- 輪替金鑰時：先在 Supabase 換，更新 GitHub Environment 的 secrets，再跑 `function` 與 `web`。`CSA_JWT_SECRET` 一換，所有人的 session 會失效，需要重新登入。

## 7. 前端託管

### GitHub Pages

`npm run deploy -- <環境> pages` 在本機 build 出可以直接發布的資料夾 `<csa-deploy>/pages-<環境>/`，**不會推送任何東西**。資料夾裡有前端檔案，加上：

- `404.html`（內容同 `index.html`）：Pages 不認得前端路由，沒有它，重新整理或直接開 `/CSA/admin` 會 404。
- `.nojekyll`：關掉 Pages 的 Jekyll 處理。
- `CNAME`：設了 `CSA_CUSTOM_DOMAIN` 才會有。

設定（部署設定檔或 GitHub variables）：

| 名稱 | 說明 |
|---|---|
| `CSA_SITE_URL` | 使用者開啟的網址，可以帶路徑，例如 `https://<帳號>.github.io/CSA`，或自訂網域 `https://csa.example.com` |
| `CSA_PAGES_BASE` | 選填。前端的路徑基底；沒填就取 `CSA_SITE_URL` 的路徑（子路徑 → `/CSA/`；自訂網域 → `/`） |
| `CSA_CUSTOM_DOMAIN` | 選填。自訂網域，會寫成 `CNAME` 檔 |
| `CSA_EXTRA_ORIGINS` | 選填。換證服務另外允許的來源，逗號分隔（例如同時測試兩個網址） |

換證服務的 CORS 只認 `scheme://host`，不含路徑。部署指令會自動從 `CSA_SITE_URL` 取出來源，再加上 `CSA_EXTRA_ORIGINS`，在 `function` 步驟寫進 Supabase 的 `CSA_ALLOWED_ORIGINS`。**改了網址後一定要重新跑 `function`**，否則登入會被 CORS 擋掉。

Windows 的 Git Bash 注意：自己手動 `VITE_BASE=/CSA/ npx vite build` 時，Git Bash 會把 `/CSA/` 當成路徑轉成 `C:/Program Files/Git/CSA/`。用 PowerShell，或加 `MSYS_NO_PATHCONV=1`。用 `pages` 步驟不會遇到這個問題。

### Vercel

`web` 步驟實作的是 Vercel（只上傳 build 出來的檔案，不需要連 GitHub repo）。需要 `CSA_VERCEL_PROJECT`。

### 選託管時要確認

- 使用者所在的網路（例如中國大陸廠區）連得到。
- GitHub Pages 的私有 repo 要付費方案，且看 repo 擁有者的方案：組織的 repo 看組織的方案，個人的 repo 看個人方案。
- 網址（`CSA_SITE_URL`）要與換證允許的來源一致。

## 8. GitHub 方案的限制（目前組織是免費方案）

免費方案的私有 repo 沒有下面這些功能，目前用替代做法：

| 功能 | 免費方案 | 替代做法與風險 |
|---|---|---|
| Environment 的 Required reviewers（部署前核准） | 不支援 | 用 `PROD_DEPLOYERS` 白名單擋。但有 repo 寫入權限的人可以改 workflow 繞過，所以**寫入權限只給信任的少數人** |
| Environment 的部署分支限制 | 不支援 | 同上：任何分支的 workflow 都讀得到 `production` 的 secrets |
| main 的 branch protection | 不支援 | 約定「一律走 PR、CI 通過才合併」，沒有系統強制 |

升級到 GitHub Team 方案後，這三項都可以改用正式的設定，建議正式上線前升級。
